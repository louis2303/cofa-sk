# 솔루션 설계
1. 원본 요구와 Docs/Analysis.md를 기준으로 Templates/Prd.md를 참조해 Docs/Prd.md를 작성한다. 사용자·목표·핵심 기능·성공 기준을 명시한다.
2. PRD를 스스로 누락·모순 검토한 후 사용자에게 검토 요청한다. 수정·재검토·승인 후 진행한다.
3. Docs/Spec.md에 기능별 입력·출력·예외·관리자/일반 사용자 권한·검증 가능한 수용 기준을 정의한다.
4. Docs/Architecture.md에 프론트와 백엔드 기술 스택 후보, 선정 근거, API/DB/화면 연결 구조, 인터페이스 계약, 인증/인가, 실행 방법을 정의한다.
5. 복잡한 계산 또는 최적화가 중요하면 Docs/Algorithm.md에 강한/약한 제약, 목적 함수, 대안, 예시 검증 사례를 작성한다.
6. Docs/Plan.md에 우선순위, 의존성, 기능별 구현 순서, 최소 동작 경로, 시간 예산을 적는다.
7. PRD↔Spec↔Architecture의 기능·데이터 필드·타입·권한·제약이 일치하는지 교차 검토한다.
8. PRD·Spec·Architecture·Algorithm·Plan 검토 시 선택한 방법, 쉬운 작동 원리, 선택 이유, 현실적인 대안 1~2개, 한계와 검증 계획을 쉬운 한국어로 요약한다. 전문용어는 예시로 설명하고 근거 없는 성능 우월성 주장은 피한다.
9. 기술·구조·알고리즘의 중대한 판단은 사용자에게 위 설명과 대안/장단점을 확인받고 승인된 문서를 기준으로 구현한다.
10. Docker는 실행·제출 제약, 재현성, 가용 자원을 고려해 사용 여부를 결정하고 필요하면 검증 방식을 명시한다.

예: FastAPI/React를 기본값으로 고정하지 않고 기존 코드·환경·복잡도·개발 시간과 대안을 비교한다.

## 계산·최적화 문제 세부 설계
- 입력 스키마(타입/단위/범위), 결정변수, 출력·목적함수의 단위와 최적화 방향(최소/최대), 필수(hard)·선호(soft) 제약을 명시한다. 필수 제약 각각을 구현 위치 및 검증 테스트와 연결한다.
- 탐욕법·규칙 기반·동적계획·정수계획·제약 충족·휴리스틱 등 **문제 규모와 허용 패키지에 맞는** 1~3개 후보를 시간·메모리·정확성 보장·실패 모드로 비교한다. 전문 솔버를 기본으로 가정하지 않는다.
- 해 상태를 불가능/가능해/현재 발견한 최선해/최적성 입증/시간초과·미완료로 구분한다. 증거 없이 '최적해'라고 쓰지 않는다. 최적화가 아닌 일반 계산 문제에는 관련 규칙만 적용한다.
- 손으로 검산 가능한 작은 사례, 명백히 불가능한 사례, 규모를 늘린 사례, 독립적인 제약·목적함수 재계산 방법을 Algorithm.md에 정의한다.
