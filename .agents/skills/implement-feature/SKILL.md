# 기능 구현
1. 현재 Spec.md, Architecture.md, Plan.md와 해당 시 Algorithm.md, 기존 코드를 확인한다.
2. 우선순위 높은 기능을 입력→처리→API/저장→화면(해당 시)까지 실제 연결되는 작은 작업으로 분해한다.
3. 로직·API·스키마·DB 접근·UI를 역할에 맞게 분리하며 프로젝트 규모에 맞는 구조를 선택한다.
4. 관리자 기능이 필요하면 관리자 UI와 API를 연결하고 서버에서 인증/권한을 검증한다.
5. 각 기능의 단위/API/예외 테스트를 직접 실행하고 실패 시 수정→재실행한다. 테스트 결과를 주장만 하지 않는다.
6. 실제 서버와 브라우저에서 핵심 경로를 확인한다. 포트·실행 명령·오류를 파악한다.
7. Docker를 사용하기로 했다면 Dockerfile/구성 파일을 작성하고 빌드 및 실행·연결을 점검한다. 불허 시 무리하게 설치하지 않는다.
8. 주요 기능 묶음이 완료되면 사용자에게 실제 구현 방식·선택 이유·대안·한계·실행한 검증을 쉬운 한국어로 요약한다. 승인된 설계와 다르게 구현했다면 차이와 영향, 변경 근거를 Docs/Analysis.md 및 관련 설계 문서에 반영한다.
9. 주요 기능 완료·오류·수정·재검증 시 Docs/Progress.md를, 파일 구조 변경 시 Filereview.md를 갱신한다.
10. 업무 의미나 중대한 아키텍처 변경은 사용자에게 근거와 영향을 제시해 승인받는다.

완료 보고: 실행된 기능, 확인한 테스트와 결과, 남은 위험을 간결히 제시한다.

## 핵심 로직 구현·디버깅
- 계산·업무 규칙·버그 수정에는 가급적 기대 동작을 검사하는 실패 테스트를 먼저 만든다. 의도한 이유로 실패하는지 확인한 후 최소 변경으로 통과시키고 인접 회귀 테스트를 실행한다. 시간·위험이 허락하지 않으면 이유를 기록하고 적절한 사후 검증을 수행한다.
- 동일 오류가 반복되면 무작정 수정안을 쌓지 않고 재현 입력, 실제 로그, 원인 가설과 반례를 재점검한다. 테스트를 삭제하거나 기대값을 느슨하게 바꿔 통과로 위장하지 않는다.
- 알고리즘의 hard 제약은 UI뿐 아니라 실제 계산/서버 로직에서 강제한다. 계산 실패·불가능·시간초과는 명확히 전달하고, feasible / best-found / proven-optimal 상태를 구별한다.
- 서비스의 실제 입력→연산→저장/API→화면에 사용자가 볼 수 있는 결과가 연결되어야 하며, 화면의 예시/더미 데이터를 구현 완료로 간주하지 않는다.
